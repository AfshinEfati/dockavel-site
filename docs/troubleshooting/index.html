TROUBLESHOOTING

Diagnose first, rebuild second

Most local-environment problems fall into a few buckets: Docker, Compose configuration, a stopped service, local routing, or network/source access. Dockavel exposes checks for each without starting with destructive cleanup.

Start here

./dockavel doctorsystem + stack + sources
./dockavel source:testsources only
docker compose ps -acontainer state
docker compose configresolved Compose config
./dockavel project:listproject metadata

Port 80 is already in use

Nginx is the core local gateway and expects host port 80. Doctor reports whether port 80 is available, owned by dockavel-nginx, another Docker container, or another host listener.

!
Do not stop random services blindly

Identify the owner first. If another project intentionally needs port 80, decide which local gateway should own it.

A regional mirror cannot pull an image

  1. Run ./dockavel source:test.
  2. Check whether the Docker registry itself is reachable.
  3. Confirm the mirror actually proxies the required public upstream image.
  4. If needed, re-run ./setup.sh and explicitly select another preset or Custom endpoints.

Dockavel intentionally does not hide a fallback to an unrelated registry.

Composer or npm fails

Use source:test to separate endpoint reachability from a project dependency problem. The test checks the configured Composer repository metadata endpoint and npm registry, including response status and latency.

Doctor says “IPv4 works”

The normal/default connection path failed but an IPv4-only retry succeeded. This usually points to a broken default/IPv6 route rather than a completely unavailable source. Dockavel reports the condition but does not modify DNS or networking.

A service is enabled but not running

inspectcompose
grep '^COMPOSE_PROFILES=' .env
docker compose config
docker compose ps -a

If the profile is intentionally enabled, start the configured stack:

bashstart
docker compose up -d

If runtime images need rebuilding:

bashbuild + start
docker compose up -d --build

Add a service without deleting the stack

Re-run:

bashincremental
./setup.sh

Keep the existing profiles selected and add the new service. Compose reuses unchanged containers, named volumes and build cache whenever possible.

Local domain does not resolve

After project:add or changing a domain with project:edit, make sure the printed hosts entry exists on the host machine:

hostsexample
127.0.0.1 my-api.local

Windows hosts file:

Windowsadministrator
C:\Windows\System32\drivers\etc\hosts

If Windows still caches an old result:

CMDDNS cache
ipconfig /flushdns

Nginx validation fails during project changes

Project Manager validates Nginx before finalizing generated registration. Add/edit/remove operations are designed to roll back their Dockavel metadata and Nginx files when the new state cannot be applied safely.

↺
Look for unrelated manual configs too

Nginx validates the whole configuration, so a manually created broken file in nginx/conf.d/ can make a project operation fail even when the newly generated file is correct.

docker exec says “No such container”

Remember the three names for a PHP runtime:

PHP 8.5names
Compose service : php85
Container name  : dockavel-php85
Local image     : dev-stack-php85

Preferred command:

bashrecommended
docker compose exec php85 bash

Direct Docker form, when needed:

bashcontainer name
docker exec -it dockavel-php85 bash

Data safety

✓
Normal shutdown keeps database volumes

docker compose down stops and removes containers/networks created by Compose but does not remove named database volumes.

safe normal shutdownkeeps volumes
docker compose down
!
Destructive cleanup

docker compose down -v removes named volumes. Use it only when you intentionally want fresh local database state.

destructiveremoves volumes
docker compose down -v

project:remove is unrelated to volume cleanup: it removes only the project's .dockavel.yml and generated Nginx registration, never the source directory.

WSL / Docker Desktop connectivity

If the Docker CLI itself behaves unexpectedly inside WSL, verify Docker Desktop is running, WSL integration is enabled for the distribution, and docker info succeeds before debugging application containers. Doctor's Docker CLI/daemon checks make this distinction visible.

رفع اشکال

اول تشخیص، بعد rebuild

بیشتر مشکل‌های محیط local به چند دسته برمی‌گردند: Docker، Compose config، سرویس متوقف، routing محلی یا دسترسی شبکه/source. Dockavel برای هرکدام مسیر بررسی دارد و از پاکسازی مخرب شروع نمی‌کند.

از اینجا شروع کن

./dockavel doctorسیستم + استک + source
./dockavel source:testفقط sourceها
docker compose ps -aوضعیت container
docker compose configCompose نهایی
./dockavel project:listmetadata پروژه‌ها

پورت 80 اشغال است

Nginx gateway اصلی local است و روی پورت host 80 کار می‌کند. Doctor مشخص می‌کند پورت آزاد است، دست dockavel-nginx است، container دیگری گرفته یا process دیگری روی host گوش می‌دهد.

!
سرویس‌ها را شانسی stop نکن

اول مالک پورت را پیدا کن. اگر پروژه دیگری عمداً port 80 می‌خواهد، باید تصمیم بگیری کدام local gateway مالک آن باشد.

Mirror منطقه‌ای image را pull نمی‌کند

  1. ./dockavel source:test را اجرا کن.
  2. ببین Docker registry reachable هست یا نه.
  3. بررسی کن mirror واقعاً image عمومی upstream موردنیاز را proxy می‌کند.
  4. در صورت نیاز ./setup.sh را دوباره اجرا و صریحاً preset دیگر یا Custom endpoints را انتخاب کن.

Dockavel fallback مخفی به registry دیگر انجام نمی‌دهد.

Composer یا npm fail می‌شود

با source:test اول endpoint را از مشکل dependency خود پروژه جدا کن. Composer metadata endpoint و npm registry با status و latency بررسی می‌شوند.

Doctor می‌گوید “IPv4 works”

یعنی مسیر اتصال عادی fail شده ولی retry فقط با IPv4 موفق بوده. معمولاً مشکل از default/IPv6 route است، نه اینکه source کاملاً قطع باشد. Dockavel فقط تشخیص می‌دهد و DNS یا networking را تغییر نمی‌دهد.

سرویس فعال است ولی running نیست

inspectcompose
grep '^COMPOSE_PROFILES=' .env
docker compose config
docker compose ps -a

اگر profile عمداً فعال است:

bashstart
docker compose up -d

اگر runtimeها نیاز به build دارند:

bashbuild + start
docker compose up -d --build

اضافه کردن سرویس بدون حذف استک

bashincremental
./setup.sh

profileهای قبلی را انتخاب نگه دار و سرویس جدید را اضافه کن. Compose تا جای ممکن containerهای بدون تغییر، volume و build cache را reuse می‌کند.

دامنه local resolve نمی‌شود

بعد از project:add یا تغییر domain در project:edit مطمئن شو entry چاپ‌شده داخل hosts سیستم وجود دارد:

hostsexample
127.0.0.1 my-api.local

مسیر Windows:

Windowsadministrator
C:\Windows\System32\drivers\etc\hosts

اگر Windows هنوز نتیجه قدیمی را cache کرده:

CMDDNS cache
ipconfig /flushdns

Nginx validation در تغییر پروژه fail می‌شود

Project Manager قبل از نهایی کردن registration، Nginx را validate می‌کند. Add/edit/remove اگر نتوانند state جدید را با امنیت apply کنند، metadata و Nginx config خودشان را rollback می‌کنند.

↺
configهای دستی دیگر را هم بررسی کن

Nginx کل configuration را validate می‌کند؛ پس یک فایل دستی خراب در nginx/conf.d/ هم می‌تواند عملیات پروژه را fail کند.

docker exec می‌گوید “No such container”

PHP 8.5names
Compose service : php85
Container name  : dockavel-php85
Local image     : dev-stack-php85

دستور ترجیحی:

bashrecommended
docker compose exec php85 bash

فرم مستقیم Docker:

bashcontainer name
docker exec -it dockavel-php85 bash

امنیت داده‌ها

✓
shutdown عادی volume دیتابیس را نگه می‌دارد

docker compose down container/network را پایین می‌آورد ولی named volume دیتابیس را حذف نمی‌کند.

safe normal shutdownkeeps volumes
docker compose down
!
پاکسازی مخرب

docker compose down -v volumeها را حذف می‌کند. فقط وقتی استفاده کن که عمداً دیتابیس local تازه می‌خواهی.

destructiveremoves volumes
docker compose down -v

project:remove هیچ ارتباطی با پاکسازی volume ندارد؛ فقط .dockavel.yml و Nginx registration پروژه را حذف می‌کند و سورس باقی می‌ماند.

اتصال WSL / Docker Desktop

اگر خود Docker CLI داخل WSL مشکل دارد، قبل از debugging پروژه مطمئن شو Docker Desktop روشن است، WSL integration برای distro فعال است و docker info جواب می‌دهد. Doctor همین تفاوت Docker CLI و daemon را مشخص می‌کند.
